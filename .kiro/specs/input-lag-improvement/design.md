# 設計文書

## 概要

otak-lsp拡張機能の入力ラグ改善機能は、高速な日本語入力時に発生する解析競合を解決し、ユーザー体験を向上させる。現在のシステムでは、複数の解析が同時実行されることで処理が重複し、古い解析結果が新しい結果を上書きする問題が発生している。

この設計では、解析の直列化と結果の最新性チェックを導入することで、これらの問題を解決する。

## アーキテクチャ

### 現在のアーキテクチャの問題点

```
文書変更 → デバウンス → 解析実行（並列）
    ↓         ↓         ↓
  変更A    タイマーA   解析A（遅い）
  変更B    タイマーB   解析B（速い）
  変更C    タイマーC   解析C（速い）
    ↓         ↓         ↓
  結果順序: B→C→A（古い結果Aが最後に反映される）
```

### 新しいアーキテクチャ

```
文書変更 → 解析状態管理 → 直列化された解析実行
    ↓           ↓              ↓
  変更A    状態更新A        解析A（実行中）
  変更B    状態更新B        解析B（待機）
  変更C    状態更新C        解析C（待機、Bを上書き）
    ↓           ↓              ↓
  結果: A完了 → C実行（最新のみ）
```

## コンポーネントと インターフェース

### AnalysisState インターフェース

```typescript
interface AnalysisState {
  running: boolean;           // 解析実行中フラグ
  pending: boolean;          // 待機中解析フラグ
  latestDocument: TextDocument | null;  // 最新の文書状態
  latestVersion: number;     // 最新の文書バージョン
  lastChangeAt: number;      // 最後の変更時刻（ミリ秒）
}
```

### AnalysisManager クラス

```typescript
class AnalysisManager {
  private analysisStates: Map<string, AnalysisState>;
  private debounceTimers: Map<string, NodeJS.Timeout>;
  
  scheduleAnalysis(document: TextDocument): void;
  private runAnalysis(uri: string): Promise<void>;
  private shouldProcessResult(uri: string, analysisVersion: number): boolean;
  clearState(uri: string): void;
}
```

### 既存コンポーネントの変更

- **main.ts**: `analyzeDocument`関数にバージョンチェック機能を追加
- **debounceTimers**: 既存のタイマー管理を維持
- **documentTokens等のキャッシュ**: 最新性チェック後のみ更新

## データモデル

### 解析状態の管理

```typescript
// グローバル状態
const analysisStates: Map<string, AnalysisState> = new Map();

// 初期状態
const initialState: AnalysisState = {
  running: false,
  pending: false,
  latestDocument: null,
  latestVersion: 0,
  lastChangeAt: 0
};
```

### 解析フロー

1. **スケジューリング段階**
   - 文書変更イベント受信
   - 解析状態の更新（最新文書、バージョン、変更時刻）
   - 実行中チェック（running === true なら pending = true のみ）
   - 非実行中ならデバウンスタイマー設定

2. **実行段階**
   - 状態を running = true に設定
   - 解析対象の文書とバージョンを確定
   - 実際の解析処理実行
   - 完了時に running = false に設定

3. **結果反映段階**
   - 文書バージョンの最新性チェック
   - 最新の場合のみキャッシュ更新と通知送信
   - 古い場合は結果を破棄

## 正確性プロパティ

*プロパティとは、システムのすべての有効な実行において真であるべき特性や動作の形式的な記述です。プロパティは人間が読める仕様と機械で検証可能な正確性保証の橋渡しをします。*

### プロパティ1: 解析の直列化

*任意の* 文書URIに対して、解析が実行中の場合、新しい解析要求は待機状態に設定され、同時実行されない
**検証対象: 要件 1.1, 1.2**

### プロパティ2: 最新要求の優先

*任意の* 文書に対して複数の解析要求が待機している場合、最新の文書状態のみが解析対象となる
**検証対象: 要件 1.3**

### プロパティ3: 古い結果の破棄

*任意の* 解析結果について、完了時に文書バージョンが変更されている場合、診断送信、セマンティック更新、キャッシュ更新のいずれも実行されない
**検証対象: 要件 2.1, 2.2, 2.3, 2.4**

### プロパティ4: 状態管理の一貫性

*任意の* 文書URIに対して、解析状態が適切に管理され、文書クローズ時に状態が削除される
**検証対象: 要件 3.1, 3.2**

### プロパティ5: デバウンス動作の維持

*任意の* 連続する文書変更に対して、適切なデバウンス遅延が適用され、解析完了後の再スケジューリングで残り時間が正しく計算される
**検証対象: 要件 4.1, 4.2, 4.3**

### プロパティ6: 機能互換性の保証

*任意の* 設定状態において、文法チェックとセマンティックハイライトが有効な場合、最新の解析結果に基づいて適切な通知が送信される
**検証対象: 要件 5.1, 5.2, 5.3**

### プロパティ7: 最終一貫性の保証

*任意の* 連続編集シーケンス後、最終的に診断とセマンティックハイライトが最新の文書内容と一致する
**検証対象: 要件 6.2, 6.3**

## エラーハンドリング

### 解析エラー時の処理

- 解析中にエラーが発生した場合、`running`フラグを`false`に戻す
- 待機中の解析がある場合は、適切な遅延後に再スケジュール
- エラー状態でもキャッシュクリアと診断クリアを実行

### タイマー管理エラー

- タイマー設定失敗時は即座に解析実行
- タイマークリア失敗は無視（重複実行防止のため）

### メモリリーク防止

- 文書クローズ時の確実な状態削除
- 長時間残存する解析状態の定期クリーンアップ（オプション）

### プロパティベーステスト

プロパティベーステストでは、fast-checkライブラリを使用し、各テストで30回の実行を行う。

- **プロパティ1テスト**: ランダムな解析要求シーケンスで直列化動作を検証
- **プロパティ2テスト**: ランダムな複数要求で最新優先動作を検証
- **プロパティ3テスト**: ランダムなバージョン変更で結果破棄動作を検証
- **プロパティ4テスト**: ランダムな文書操作で状態管理の一貫性を検証
- **プロパティ5テスト**: ランダムな変更タイミングでデバウンス動作を検証
- **プロパティ6テスト**: ランダムな設定変更で機能互換性を検証
- **プロパティ7テスト**: ランダムな編集シーケンスで最終一貫性を検証

各プロパティテストは以下の形式でタグ付けする：
**Feature: input-lag-improvement, Property {number}: {property_text}**
